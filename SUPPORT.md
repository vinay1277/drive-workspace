# Support

How to get help with `drive-workspace` as a developer integrating it into
a host application or contributing to the library itself.

> **Status**: pre-v0.1.0. The package's public API is explicitly unstable
> per [ADR-0009](docs/decisions/0009-versioning-and-distribution.md).
> Don't pin to specific behaviours that aren't covered by tests until v0.1.0.

---

## Step 1 — try self-serve first

Before opening an issue or pinging anyone, please check these. They cover
~80% of questions a host-app developer asks:

| Question | Document |
|----------|----------|
| What is `drive-workspace`? What problem does it solve? | [`docs/architecture.md`](docs/architecture.md) §1-3 |
| Why does it work the way it does (security model, plug points, etc.)? | [`docs/decisions/`](docs/decisions/) — 11 ADRs, scan titles, read what's relevant |
| What's the public API? | `backend/docs/_build/html/index.html` (generated by `sphinx-build` — `cd backend && pip install -e .[docs] && sphinx-build -b html docs docs/_build/html`) |
| How do I integrate this into my host app? | [`integration-tests/smartmeter/`](integration-tests/smartmeter/) — working sketch with ~80 lines of host glue |
| Backend wire contract (what the Android client expects from the host's backend) | [`android/library/docs/BACKEND_CONTRACT.md`](android/library/docs/BACKEND_CONTRACT.md) |
| How is the test bed wired (Workspace, Shared Drive, SA, env vars)? | [`docs/deployment.md`](docs/deployment.md) |
| Common errors and their fixes | [`docs/troubleshooting.md`](docs/troubleshooting.md) ← **start here for runtime errors** |
| What's done, what's next, what's the plan? | [`docs/plan.md`](docs/plan.md) |
| How do I work in this repo (sessions, briefs, ADRs)? | [`docs/operating-guide.md`](docs/operating-guide.md) |

If your question isn't answered after 10 minutes of looking, it probably
isn't covered — open an issue.

## Step 2 — open a GitHub issue

Primary support channel: **GitHub Issues on this repo.**

Why issues over Slack/email:

- Searchable history. Future devs hit the same problem; they find your issue.
- Forces problem-statement discipline (good for everyone).
- Pre-merge discussion happens in the same thread as the eventual fix.

### How to write a useful issue

Three categories, three templates:

**(a) Bug — something doesn't work as documented**

```
## Symptom
[What you observed]

## Expected
[What you thought would happen, per which doc/ADR]

## Reproduction
[Minimal steps. Include OS, Python/Kotlin version, drive_workspace version
(`pip show drive_workspace` or git SHA), and the actual command/code that fails.]

## Logs
[Stack trace, server log, adb logcat — whatever's relevant]

## What I tried
[Anything you investigated before opening this]
```

**(b) Question — "is X possible?" / "should X work this way?"**

```
## What I'm trying to do
[Goal at the host-app level]

## What I tried
[Code/config attempt]

## What's confusing
[The specific thing the docs don't answer]
```

Tag with `question` label.

**(c) Feature — something doesn't exist yet**

```
## Use case
[The host-app scenario that needs this]

## Proposed surface
[What you'd want the API to look like]

## Workaround today
[How you're getting by without it; helps prioritise]
```

Tag with `enhancement` label.

### Triage expectations

| Severity | Response | Resolution target |
|----------|----------|-------------------|
| Blocker (can't work around) | Same business day | Same week |
| Bug (can work around) | 2-3 business days | Within the next session that lands code |
| Question | Same week | Same week |
| Feature | Same week (acknowledgment) | Per the project roadmap; usually queued behind in-flight phases |

This is best-effort, not a contract. Pre-v0.1.0 the project is staffed
part-time.

## Step 3 — direct contact (urgent only)

If something is genuinely blocking *and* time-sensitive, ping the
maintainer directly:

- **Maintainer**: <fill-in-your-name>
- **Email**: <fill-in-your-email>
- **Other channel** (Slack/Teams/etc.): <fill-in-channel>

Use this for: production incident on a host app that depends on
`drive-workspace`, security disclosure, anything you can't say publicly.

For everything else, the GitHub Issue path keeps the conversation
durable and benefits the next person.

## Security disclosure

If you believe you've found a security issue (credential leak, auth
bypass, scope escalation, etc.), **do not open a public GitHub Issue**.
Email the maintainer directly. We'll coordinate on the fix and
disclosure timing.

## Contributing

Contributions go through the same channels:

- Bug fixes: PR linked to a tracked Issue
- Features: open an Issue first to discuss the surface; then PR
- Docs / typos: just send a PR

Read [`docs/operating-guide.md`](docs/operating-guide.md) and
[`docs/decisions/0007-docs-as-memory-sessions-as-workers.md`](docs/decisions/0007-docs-as-memory-sessions-as-workers.md)
before any non-trivial change. The repo runs on a session-brief +
ADR discipline that's easy to violate accidentally.

## What this repo is *not*

To set expectations:

- **Not open source.** Proprietary, in-house only. See [`LICENSE`](LICENSE).
- **Not v1.0 stable.** The public API is unstable until v0.1.0 is tagged
  and even then "stable" means "we'll deprecate before breaking."
- **Not a turnkey product.** It's plumbing. Host apps still write ~80
  lines of glue. See the SmartMeter sketch.
- **Not Drive UI / Drive client SDK.** It's an upload/folder/log helper
  for backend services. If you want to build a Drive UI, use the official
  Google Drive SDKs.
- **Not a substitute for OAuth user-flow** if your host needs user-owned
  Drive content. `drive-workspace` is server-mediated SA-backed by design.
